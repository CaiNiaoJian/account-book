## 2. 自动化验证

| 项目 | 结果 |
|---|---|
| `pytest` | **318 项全绿**（新增 36 项 P2 用例） |
| `ruff check` + `format --check` | 通过 |
| `tsc --noEmit` | 通过 |
| `vite build` | 通过 —— 主包 **194 KB**（gzip 57 KB），ECharts 独立分包 579 KB（gzip 195 KB） |
| PyInstaller 打包 + 冒烟 | 通过（56.2 MB） |

P2 新增用例的重点（都是"会悄悄算错"的地方）：

* **净值累计**：跨日累加、转账不改变净值、删除后回滚；
* **回填历史流水**必须让此后每一天的净值都跟着变（这是增量重算最容易漏的一条）；
* 改账户起点余额要追溯影响整条曲线；
* 六类指标都能算，且分级由服务端给出、零值单独占据 0 档；
* **异常分数用中位数基线**：造一个 60 倍的离群值，正常的 1.2 倍消费仍不该被判为异常；
* 分级用分位数：五个递增值必须铺满四档（固定阈值会让色域用不满）；
* 阶梯曲线的拐点落在流水真实时刻（09:00 / 18:00），不是按小时插值；
* 当日构成遵守"分账优先"；变动归因排除转账；
* 手动校准过的快照不被自动日结覆盖；
* 卡片墙分组与信用额度可用额计算；拖拽重排"全成功或全失败"；
* 卡面配方校验（非法颜色 / 未知纹理 / 色标不足都被拒绝）；
* 内置机构与内置卡面不可删除，被账户引用时也不可删除。

## 3. 本轮修掉的真实缺陷

| # | 问题 | 症状 | 根因与修复 |
|---|---|---|---|
| 1 | **异常分数的基线算错基准** | 数值"看起来有"，区间深处的日期却拿到区间之外的参照 | 原实现以"重算区间起点"向前回溯 8 周；改为**逐日回溯**，并把查询窗口一并扩出 8 周 |
| 2 | 分级只用到 4 档 | 最高一档跨了 40% 的分布，颜色看起来"跳" | 用了 4 个切点却只有 4 个非零档位；改为三个四分位切点 + 零值单独一档 |
| 3 | **卡片墙的卡面全部不可见** | 分组标题与小计都在，卡片是空白 | `Reorder.Item` 挂了 `variants` 但没有父级驱动 `initial`/`animate`，卡片停在 `opacity: 0`。不报错、类型检查也过，只能靠肉眼发现 |
| 4 | 星期标签错位 | "一/三/五"落在格子行之间 | 标签列用 `justify-between` 按容器高度（含图例）分布；改为与网格同为 7 行 × 11px + 3px |
| 5 | ECharts 被打进主包 | 主包从 140 KB 涨到 773 KB，而记账页根本用不到图表 | 在 `manualChunks` 中拆出 `vendor_charts` |
| 6 | 两套日历接口 | `/api/stats/calendar` 与 `/api/calendar` 返回不同形状，口径会分叉 | 删除旧接口，流水页的月视图改用统一的日历数据（并因此获得了同样的分级） |
| 7 | 构建在 `%TEMP%` 失败 | `esbuild ... Access is denied` | 环境 ACL 导致 esbuild 无法清理临时文件；构建脚本把 `TEMP` 指向工作区内目录 |

## 5. 明确的已知局限（写出来而不是藏起来）

1. **计划中的"12 类图表"目前落地了 4 类**（环形构成、阶梯曲线、柱状、折线趋势），
   其余（瀑布图、旭日、桑基、雷达、矩形树、箱线、气泡、预算仪表盘）留到 P3–P6 ——
   它们分别依赖 K 线、薪酬、预算等尚未存在的数据，现在画只能是示意图形，
   而"看起来有数字其实是编的"正是本项目一开始就拒绝的做法；
2. **可拖拽仪表盘未做**：首页目前是固定布局；
3. **动效体系只覆盖了已实现的部分**（数字与列表入场、卡片拖拽反馈、图表入场），
   计划里的"日历格子波次点亮""蜡烛图逐根生长"等随对应图表一起做；
4. `has_attachment` 角标目前只认事件日志的附件，流水附件在 P8 接入后自动生效；
5. 日结缓存在首次打开年历时需要一次全区间计算（几百毫秒）。
