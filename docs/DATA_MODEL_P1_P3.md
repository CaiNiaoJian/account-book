## 2. 几个刻意的设计决定

### 2.1 周期记账只存"怎么重复"，不预先铺流水

把未来十年的流水提前写进 `transactions` 是错的：改一次规则就得删掉几千行，
而且那些行在被生成之前**并不是"发生过的事实"**。

`next_due_date` 是**算出来的缓存**，可以随时由规则 + 上次生成日重建。
它的存在只是为了让"哪天该提醒"能一次查询拿到，而不是每次全表推算。

发生日**每次从起点重算**，而不是"上一次加一个周期"：
后者会累积误差 —— 1 月 31 日 +1 月 = 2 月 28 日，再 +1 月 = 3 月 28 日，
用户的"每月 31 日"会永久变成 28 日。

### 2.2 预算的"已用金额"不落库

它是流水的函数。存一份就要在**每次**记流水时同步，一旦漏了，
用户会看到一个不动的进度条 —— 比没有进度条更糟。

只有"上期结转额"这个**跨期结果**被缓存到 `carryover_minor`，
因为它需要回溯整个上一期，而它只在期间切换时变化。

`budgets` 上有一个分区唯一索引（`sqlite_where=deleted_at IS NULL AND enabled = 1`）：
同一个适用范围只允许一条启用中的预算。允许两条会让"这个月到底按哪个算"
永远说不清，而这正是预算最不该含糊的地方。

### 2.3 债务的本金与利息必须分开存

把一笔还款记成"已还 3000"之后，**就再也算不出"还剩多少本金"** ——
而那是债务最核心的一个数，用户打开那一页就是想知道它。

因此 `debt_payments` 把 `principal_minor` 与 `interest_minor` 分开存，
`amount_minor` 只是二者的和（冗余但便于累加与对账）。
登记还款时若两者都不给，**整笔视为本金**：这是最常见的记账方式，
也是最安全的默认 —— 记成利息会凭空产生支出，记成本金只是保守。

### 2.4 `asset_ohlc` 是纯聚合缓存

它没有引入任何新口径，只把 `daily_stats.net_worth_minor` 按周期折成
开高低收 + 资金流动额。因此它可以随时删掉重算，
也与日结共用一套失效逻辑（日结重算时顺带作废重叠区间）。

口径细节见 [KLINE_METRICS.md](KLINE_METRICS.md)。

### 2.5 模板的 `tag_ids` 用 JSON 数组而不是关联表

标签只在**套用模板时整体读取**一次。为它单开一张关联表会让
"套用模板"变成三次查询，而收益只是理论上的规范化。

真要做标签统计时走的是 `transaction_tags`，与这里无关。

模板存**整套字段**而不是"只存差异"：模板的用途就是一键填完整个表单，
只存差异的话用户还得自己补齐剩下的字段，那就没省下什么。

模板允许 `amount_minor IS NULL`，表示"只填结构"——
例如"打车"这个模板，金额每次不同。

## 3. 与既有约定的一致性

* **金额一律整数最小单位**（`*_minor`），模板与债务也不例外；
* **业务时间**（`debt_payments.occurred_at`）是本地墙上时钟 + `tz_offset_minutes`，
  与流水同义；`created_at` / `updated_at` 仍是 naive UTC；
* 新增的用户数据目录与文件全部进 `.gitignore`（本轮无新增目录）；
* 服务层的校验都在**保存时**完成，而不是等到"用到的那天"：
  周期规则引用的账户与分类若不存在，立刻报错 ——
  让它到生成那天才失败，用户会白等一个月。
