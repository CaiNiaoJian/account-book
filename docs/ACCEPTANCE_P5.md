# P5 验收：台账与报表

对应需求 21。本文只写**可验证的判据**，以及几处"看起来可以那样做、
实际不能"的设计取舍。

## 1. 交付范围

| 能力 | 状态 |
| --- | --- |
| 台账：期初 + 逐笔（滚动余额）+ 期末 | ✅ |
| 余额连续性校验（内部自洽 + 与聚合口径一致） | ✅ |
| 试算平衡（转账中性、调整计入、破损转账可审） | ✅ |

| 导出：Markdown / 自包含 HTML / PDF / PNG 摘要图 | ✅ |
| AI 分析：SSE 流式 + 离线回落 + 脱敏 | ✅ |
| 零数据空状态 | ✅ |

## 2. 可验证判据

### 2.1 台账

* **期末必须等于聚合余额。** 这是台账存在的全部意义 —— 一本对不上的账
  比没有账更糟，因为用户会拿它当依据。
* **排序必须带 `id` 兜底。** 同一天同一秒记两笔账完全正常（导入、批量录入）。
  只按 `occurred_at` 排序时两行先后取决于数据库返回顺序，而它并不保证稳定 ——
  滚动余额会时对时错，"期初 + 逐笔 = 期末"也会偶发失败。
* **转账的转入腿必须计入。** 漏掉它会让台账少算每一笔转入
  （表现为"转账进来之后余额没变"）。
* **`status='void'` 不计入，但笔数要报出来。** 用户记了 10 笔而台账只有 8 笔时，
  必须能知道那 2 笔去哪了。
* **校验比的是"截至区间末的余额"**，不是 `account_balance`（全时段聚合）。
  用户可以先记明天的账，用错的那个比会让校验报"台账不一致" ——
  **一个天天报假警的校验，用户看两次之后就再也不看了**，
  那比没有校验更糟，因为它把"真的不一致"也一起淹掉了。
  未来日期的流水单列成 `future_dated_count` / `future_dated_net_minor`。
* **对账生成 `adjust` 分录而不是直接改余额。** 余额是算出来的，没有可以直接改的
  地方；更重要的是**差异本身是信息** —— 直接改会把"少记了 37.5 元"悄悄抹掉。
  差异为 0 时不建流水。
* **`adjust` 计入余额但不计入收支。** 因此试算平衡的恒等式必须写成
  "账户变动之和 = 收入 − 支出 **+ 调整净额**"，漏掉调整会让体检在每次对账之后
  都报假警。

### 2.2 报告 Schema

* **后端只产出中性数据集，绝不产出 ECharts option。**
  否则每个导出渲染器都得先"读懂 ECharts"才能画出任何东西，
  而它们真正需要的是数据；schema 也会绑上某个图表库的版本。
* **块是唯一的扩展点**（`text | metrics | table | chart | note | unavailable`）。
  四个消费者（界面 / Markdown / HTML / PDF）都只读块结构，
  没有任何 `if section == 'breakdown'` 这类分支。
* **`unavailable` 块：诚实优先于好看。** P6 的薪酬节明确写"这一节尚未实现"，
  **不放一排 0** —— 那会让用户以为"我这个月五险一金是 0"。
  一个填满假零的报告比缺一节的报告危险得多。
* **占比由后端算好随行下发。** 让每个渲染器各算一遍，必然有一处算错，
  而"表格里的占比加起来不是 100%"很难被发现。
* **上一期为 0 时变化率返回 `None`**："从 0 涨到 100"没有可表达的百分比，
  返回 0 会谎称"没有变化"。
* **同比：日/周按 364 天回退**（恰好 52 周，星期几不变），月度/年度按日历年。
  按 365 天回退会让"本周"对上"去年的周二到下周一"。
* **完整度只统计今天及之前** —— 把未来还没到的日子算成"漏记"是在冤枉用户。
* **"未分类"（`category_id = None`）作为一档真实分类保留**，
  合并进"其它"会掩盖"我有多少笔没分类"。
* **空表必须带一句说明**：一张只有表头的表会让人以为加载失败。

### 2.3 导出

* **HTML 必须自包含**：无 `<link>`、无 `<script>`、无任何外部请求。
  导出的文件可能被拷到另一台机器、或者几年后再打开。
* **HTML 必须转义一切来自数据库的文本**（含 SVG 的 `aria-label` 属性上下文）。
  安全性质是"**没有裸标签存活**"，而不是"那段文字不出现" ——
  转义后 `onerror=alert` 仍以纯文本留在页面上，那是无害且正确的。
* **Markdown 带 BOM**：Windows 记事本按本地代码页打开无 BOM 的 UTF-8 会乱码，
  而这个文件很可能就是被双击打开的。
* **PDF 用 reportlab 内置 CID 字体**（`STSong-Light`），不需要附带字体文件 ——
  分发时少一个几 MB 的资源，也少一处"路径找不到"的失败点。
* **导出响应带 `Cache-Control: no-store`**：报告依赖"今天"。
* **图表在 Markdown / PDF 里落成表**（同一个 `dataset`），在 HTML 里画成内联 SVG。
  这正是"中性数据集"要支持的事：导不出图时数据仍然完整。

### 2.4 AI 分析

* **离线回落是默认路径，不是错误路径。** 没有 key、断网、超时、服务端报错 ——
  每一种情况下用户都拿到**能用的内容**，且 `source` / `fallback_reason`
  如实返回，界面明说"这次是离线规则分析"。
  让用户以为是模型说的、实际是几条 if-else，那才是真的欺骗。
* **商户名、备注、单笔金额从来不进 payload。** 不是"默认脱敏所以小心"，
  而是 `build_summary` 根本不构造这些字段 ——
  **一个不存在的字段不可能被漏脱敏。**
* **脱敏只做两件事**：去掉绝对金额（只留比例）、替换用户自取的名字
  （预算/罐子/账户 → 代号）。**分类名保留**，否则分析什么也说不出来。
* **规则洞察的 `evidence` 被丢弃**：那些字符串里嵌着原始金额。
* **密钥只返回 `has_key`**，永远不回传 key 本身。
  `api_key` 是三态：不传=保持，空串=**清除**，有值=替换。
* **离线与联网走同一套 SSE 帧**，前端只有一条渲染路径。
  帧用 `ensure_ascii=False`（否则中文变 `\uXXXX`，抓包时不可读），
  按**字符**切块（按字节切会把汉字切成两半）。

### 3.1 打包产物的报告导出实测

`.smoke-test/verify-frozen-reports.ps1` 启动 `dist\AccountBook\AccountBook.exe`，
取到端口与令牌后**真的取回文件并检查内容**：

```
[ok]   创建一笔流水
[ok]   JSON 报告可构建
[ok]   台账与试算平衡
[ok]   导出 Markdown（含中文，且带 BOM）
[ok]   导出 HTML（自包含）
       PDF 11348 字节，魔数 %PDF-
[ok]   导出 PDF（冻结环境下的 reportlab）
[ok]   AI 分析在没有 key 时回落离线
```

这一项是刻意加的：`packaging/accountbook.spec` 的 `hiddenimports` 与 `datas`
都**没有**提到 reportlab，依赖的是 PyInstaller 自带的 hook。
"通常会收集"不是"已验证" —— 一个能启动、能开页面却导不出 PDF 的构建，
只有在真的点一次导出时才会暴露。

## 4. 本文档记录的缺陷（都由验证抓到）

1. **路由顺序把自己坑了**：`/api/ledger/{account_id}` 声明在
   `/api/ledger/trial-balance` **之前**，FastAPI 按声明顺序匹配，
   于是后者被当成 `account_id="trial-balance"`，永远返回 422。
   这类 bug 的特点是**端点存在、文档里有、看起来也"有响应"**。
2. **校验用了全时段余额**（见 2.1）。
3. **用例三次栽在"日期相对今天偏移 + 区间是自然月"**上：
   今天若是 1 号，月度区间只有一天，那些"18 天前"的记账日落在区间外，
   于是用例"月初失败、月中通过"。已改为显式 `custom` 窗口。
4. **截图抓到三个界面问题**：每日支出图的轴标签挤成一团、
   转账行的摘要显示成 `— →支付宝`、以及**台账截图一直只显示空状态**
   （默认账户没有流水，于是表格这条渲染路径一次都没被看到过）。
   最后一条尤其值得记：**152 项用例都没能让这个页面被看一眼**，
   而"表格渲染出来长什么样"恰恰是测试覆盖不到的那部分。
5. **我第一次的 XSS 检查是无效的**：用恶意商户名建流水后断言导出的 HTML 里
   没有 `onerror=alert`，结果"通过" —— 但真正的原因是商户名根本没出现在
   周报的任何一节里。"没转义"和"文本没被渲染"在那种检查下看起来一模一样。
   改用**构造的文档**精确控制每个块的内容，才是有效的验证。

## 5. 已知未做

* **薪酬与五险一金那一节**是 `unavailable` 块（P6）。
* **PDF 里的图表是表格**，不是图形。PDF 承担"能存档、能打印"，
  HTML 承担"给人看" —— 后者已经是内联 SVG。
* **PNG 导出的是摘要图**（KPI + 首要图表），不是整份报告的长图。
  整份报告有十几张表和图表，拼成长图既看不清也不便分享。
* AI 的**联网路径**在真实服务上未做过端到端验证（本环境无可用 key）。
  协议层用 `httpx.MockTransport` 验证了请求体与响应解析，
  但"某个具体厂商的返回是否完全兼容"仍属未验证。
