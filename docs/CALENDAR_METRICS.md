# 日历与日结指标口径（P2 / REQ-20）

这份文档存在的理由：日历上的颜色与分数**必须能被解释**。
一个说不清来路的指标比没有指标更糟 —— 用户会照着它做判断，然后发现对不上。

---

## 1. 数据从哪来

| 层 | 角色 |
|---|---|
| `transactions` | **唯一事实来源**（作者权威） |
| `day_events` | 事件日志，也参与"是否登记"的判定 |
| `daily_stats` | 派生缓存：每日收支、净值、笔数、登记状态、异常分数 |
| `asset_snapshots` | 派生缓存：每日每账户收盘余额 |

缓存采用**脏标记 + 读取时懒重算**（`services/daily.py`）：

1. 任何流水或账户变更都调用 `mark_dirty_from(day)`，记下受影响的起始日；
2. 任何读取先调用 `ensure_fresh(start, end)`，把脏区间补齐后再返回。

这样正确性**不依赖调用方记得刷新**。忘记标脏只是多算一次；
忘记重算会让用户看到错数据 —— 两者严重程度差得远，所以偏保守。

**净值是累计量**：插入一笔历史流水会改变此后每一天的余额，
因此重算区间一定延伸到"今天"，而不是只算被改动的那一天。

---

## 2. 六类颜色主指标

| 指标 | `metric` | 取值 | 分级 |
|---|---|---|---|
| 是否登记收支（默认） | `entry` | `none` / `logged` / `confirmed` | 3 级 |
| 支出强度 | `expense` | 当日支出金额 | 5 级 |
| 收入强度 | `income` | 当日收入金额 | 5 级 |
| 净流入 / 净流出 | `net` | 收入 − 支出 | 发散（正 2 级 / 负 2 级） |
| 资产变化幅度 | `net_worth_change` | (今日净值 − 昨日净值) / \|昨日净值\| | 5 级 |
| 异常分数 | `anomaly` | 0–1 的偏离度 | 5 级 |

**分级由服务端计算**（分位数），不由前端定阈值。
理由：图例、格子、导出的 PNG 必须用同一套深浅标准；
前端各自定阈值的话，改一次图例就会和格子对不上，而且没人会发现。

分级规则：正值按 25 / 50 / 75 分位切成 4 档，0 单独一档（共 5 级）。
用**分位数**而不是固定阈值，是因为不同人的支出量级相差几个数量级 ——
固定阈值会让"月支出 300 的人"整月最浅色、"月支出 30 万的人"整月最深色。

---

## 3. 登记状态（`entry_state`）

| 状态 | 判定 | 颜色 |
|---|---|---|
| `none` 未登记 | 当天既无流水也无事件 | 灰 |
| `logged` 已登记 | 当天有流水或事件 | 浅色 |
| `confirmed` 已核对 | 用户显式点了「标记为已核对」 | 实心 + 白边 |

**为什么 `confirmed` 必须由用户触发**：应用无法知道"这天是不是还有没记的账"。

曾经考虑过自动判定（例如"有流水且无待清算 → 已完整登记"），但那样
`logged` 与 `confirmed` 会在绝大多数日子里重合，中间态形同虚设；
更糟的是它会给出一个**不可信**的信号（好像应用知道你没漏记）。
宁可让用户点一下，也不要撒一个看起来聪明的谎。

---

## 4. 异常分数（`anomaly_score`）

```
基线 = 当天之前 8 周内、同星期的**有记录日子**的支出中位数
ratio = 当日支出 / 基线
score = 0                    if ratio ≤ 1
      = min(1, (ratio-1)/2)  if ratio > 1      # 偏离 3 倍即封顶
      = 1                    if 无历史样本且当日有支出
```

三个刻意的选择，每一个都对应一种会误导人的做法：

| 选择 | 如果反过来会怎样 |
|---|---|
| 基线取**中位数**而非均值 | 一次大额消费会把均值抬高，之后所有正常消费都被判成"正常"（分数恒为 0）→ 指标失效 |
| 只统计**有记录的日子** | 把没记账的日子当作"花了 0"，基线被拉到 0 → 所有正常消费都成"异常" |
| 逐日回溯而非全区间共用一条基线 | 区间深处的日期会拿到错误的参照（这是实现时真实写错过的一处 bug） |

## 5. 角标

| 角标 | 来源 | 现状 |
|---|---|---|
| `events` | 当天有事件日志 | ✅ |
| `attachment` | 事件日志带附件 | ✅（流水的附件要到 P8） |
| `transfer` | 当天有转账或余额校准 | ✅ |
| `bill` | 某信用卡的账单日 | ✅ |
| `due` | 某信用卡的还款日 | ✅ |
| 发薪日 | 发薪规则 | P6 |
| 预算超限 | 预算模块 | 待预算模块 |

**不显示"永远不亮"的角标** —— 那比没有角标更让人困惑。

---

## 6. 当日详情

* **余额阶梯曲线**：从"昨日收盘净值"出发，按流水的**真实发生时刻**逐笔推进。
  用 `step: 'end'` 画直角转折，而不是斜线插值 ——
  斜线会暗示余额是连续变化的，那是错的。
* **变动归因**：只统计改变**总净值**的流水。账户间转账不改变总净值，
  因此不在此列（否则日内曲线会因为一次划转而出现虚假尖峰）。
* **构成**：与统计口径一致，**分账优先于主分类**。
* **同星期均值对比**：近 30 天同一星期的平均支出，回答"今天花得比平时多吗"。

---

## 7. 已知局限

1. `net_worth_change` 在前一日净值为 0 时返回 0（比例无定义），
   而不是编造一个无穷大或 100%；
2. 首次打开日历会触发一次全区间日结计算（几百毫秒级）；
3. 日均 < 1 笔、或长期不记账的用户，异常分数会频繁给出 1.0 ——
   这是"没有基线"的正确表现，界面上的提示文案已说明；
4. 日历一次最多查询 3 年（`/api/calendar` 会拒绝更长区间），
   避免一次渲染 1000+ 天的 DOM。
