# P6 验收 · 薪酬、五险一金与定时任务

对应 `docs/PLAN.md` 需求 18、19，以及 `docs/FEATURES.md` 的 P6 一节。

## 1. 交付内容

### 1.1 工作日日历与发薪日（`services/workdays.py`）

| 能力 | 说明 |
|---|---|
| 周末判定 | 计算得出，不落库 |
| 节假日与调休 | **只存例外**，由用户录入或批量粘贴官方公告 |
| 逐日覆盖 | `workday_calendar`，种类 `holiday` / `makeup_workday` / `custom_rest` / `custom_workday` |
| 批量导入 | 解析"休 / 班 + 日期区间 + 名称"，**无法解析的行原样返回** |
| 发薪日解析 | `fixed` / `month_end` / `last_workday` / `nth_workday` |
| 调整策略 | 周末与节假日**各有一套**（`advance` / `postpone` / `none`） |
| 置信度 | `exact` / `assumed` / `inferred` 三态，界面显式标注 |

### 1.2 薪酬（`services/payroll.py`）

* 薪资来源（多来源、优先级、入账账户、软删除与恢复）
* 组成项模板：`calc` = 固定 / 比例 / 公式，`sign` = 加项 / 减项，
  基数可选「基本工资合计」或「应发合计」
* **两趟计算**：先所有加项得应发，再所有减项（个税与五险一金代扣都基于应发）
* 工资收录表：建档存**快照**、试算不落库、重算、填写入账（幂等）、
  跳过（必须给原因）、删除
* 总览：应发 / 实发 / 个税 / 五险一金代扣 + **去年同月同比** + 逐月趋势（补全空月）

### 1.3 五险一金（`services/insurance.py`）

* 险种字典（九项标准险种，**只预置名称与结构标志，比例一律留 0**）
* 参保档案：社保基数与公积金基数分开、生效区间、软删除
* 逐月缴纳：写入幂等、比例快照、基数保底/封顶**并报出收敛原因**
* 个人账户余额（派生）：`Σ计入账户的缴纳 + Σ利息 − Σ提取`
* 提取记录（含余额不足拦截）、年度对账（系统合计 vs 官方对账单 + 差异）

### 1.4 定时任务与提醒中心（`services/scheduler.py`）

* 任务：`daily` / `weekly` / `monthly` / `once`，月度复用**同一套**工作日逻辑
* 错过处理：`startup` / `immediate` / `record_only`，补办留痕标 `caught_up`
* 补办上限：单次最多 24 次，超出时推进并明确记录"漏办超过 N 次"
* 提醒：去重键、稍后提醒**有次数上限**、跳过**必须给原因**、按目标一并不了结
* 通知中心：去重、未读数、单条与全部已读

### 1.5 报表的 `payroll` 一节

P5 时这一节是一个 `unavailable` 块（"尚未实现，不放一排 0 ——
放一排 0 会让你以为本月缴纳额真的是 0"）。P6 把它变成了真实内容：
KPI、应发实发瀑布、逐月工资表、五险一金构成表与环形、账户余额、
以及"另有 N 条草稿未计入"与"比例还没填"的提示。

### 1.6 API 与界面

* 55 个端点（`api/routes/payroll.py`）
* `/payroll`：应发实发瀑布、构成环形、单位 vs 个人、**逐年累积 + 逐月累积**、
  工资历史与同比、组成项编辑、填写/跳过、五险一金设置与年度对账
* `/scheduler`：提醒中心（强弹与三个出口）、任务列表、执行历史、通知中心
* 深链 `?insurance=1` / `?components=1` / `?new=1`

## 3. 与 `docs/FEATURES.md` 原计划的**偏离**（重要）

计划里有三条我**没有按字面实现**。这不是遗漏，是有意的，理由如下。

### 3.1 不内置法定节假日日期表

原计划：*"内置 2024–2026 法定节假日与调休，可逐日覆盖"*。

**没有内置，任何一年都没有。** 法定节假日与调休安排由国务院办公厅**每年**发布，
把它写死等于内置一份**会静默过期**的数据：2027 年用户看到的是 2026 年的安排，
而界面不会提示这一点。**一个错的发薪日比没有发薪日更糟** —— 他会据此判断钱到没到。

改为：周末由计算得出；节假日与调休作为**例外**由用户录入或批量粘贴公告
（`parse_workday_text` 支持"休 / 班 + 区间 + 名称"）。
`is_workday` 返回 `basis` 与 `confident`，**未知绝不冒充工作日**；
发薪日给出 `confidence` 三态，界面显式标注。

### 3.2 不引入 APScheduler

原计划：*"调度器（APScheduler 持久化 JobStore）"*。

改为自研的 `scheduled_tasks` + `task_runs`，原因是 P6 要解决的核心问题
APScheduler 并不覆盖：**软件根本没运行时错过的那些任务怎么办**。
自研方案把 `catch_up_policy` 做成显式选择，并把补办出来的执行留痕标
`caught_up=True` —— 用户必须能区分"当时就跑了"与"事后补的"。

代价：没有 cron 表达式的全部能力（只支持四种频率），
也没有 APScheduler 的成熟度。这一点如实记录。

### 3.3 两个进度组件未做

原计划：*"公积金首付进度、养老年限进度"*。

**没有实现。** 这两个都需要额外的前提数据（购房目标金额、法定退休年龄与已缴年限），
而它们**不能由系统推断**：退休年龄因身份与政策而异，编一个默认值会让进度条
显示一个看起来精确、实际没有依据的百分比。

已实现的相关部分：账户余额与积累、逐月累积堆叠图，以及**单位 vs 个人对比**。

## 4. 已知限制

1. **利息是账户级总额，归属未分配。** 年度对账里的利息被并入"公积金或养老"
   其中之一，因此这两个账户各自的利息可能不准。模型里没有按险种记利息的字段，
   正确做法是呈现为"未分配利息"，尚未实现。
2. **`services/schedule` 实际名为 `services/scheduler`**（`FEATURES.md` 原文如此），
   文档已更正。
3. **AI 在线路径未对真实服务商验证**（P5 遗留），P6 未涉及。
4. **托盘"最小化到托盘"仍未实现**，调度任务因此只能在软件运行期间触发；
   错过的任务靠 `catch_up_policy` 在下次启动时补办。
5. 险种比例需用户按当地政策录入，系统不提供任何预置比例（见 3.1 同源理由）。

## 5. 零数据行为

全部界面与接口在零数据下给出正确空状态：

| 位置 | 零数据表现 |
|---|---|
| `/payroll` | 空状态卡片 + "先建一个薪资来源"的可操作引导；不显示任何 0 图表 |
| 报表 `payroll` 一节 | `text` 块（"这一区间还没有工资或五险一金记录…"）+ 比例提示，**不是** `unavailable` |
| 五险一金试算 | `incomplete=True` + `unfilled_items`，界面显示"这些险种还没填比例"而非"缴得少" |
| 五险一金字典 | **空**（不预置比例）；一键铺名称后每项标 `rates_filled=false` |
| `/scheduler` | 空状态卡片；健康度 `failure_ratio=None`（**不编一个 0%**） |
| 同比 | 去年同月为 0 时返回 `null`，界面显示"—"而非 0% |
| 单位缴纳占比 | 零数据时 `employer_share=None`，不编 0% |
